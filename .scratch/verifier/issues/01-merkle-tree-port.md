# 01 — StandardMerkleTree port, pinned to the contracts fixture

Status: resolved
Type: task
Spec: ../spec.md §6
Blocked by: —

Implement `internal/merkle`: OpenZeppelin `StandardMerkleTree` v1.0.8 semantics in Go. Leaf `keccak256(bytes.concat(keccak256(abi.encode(id, account, amounts[5]))))`; the encoding is fully static (7 words, 224 bytes, no offsets, no dynamic tails) so write the 224-byte serialiser directly — do not build a general ABI encoder. Sort leaves by leaf hash (`sortLeaves: true`), build a complete binary tree in a flat `2n-1` array with commutative sorted-pair hashing, root at index 0. Proof generation too: the Verifier does not submit proofs, but generating them is how we prove the tree shape matches rather than merely the root.

First, because it is the only piece provable before NUTZ exists, and because ADR-0001 accepted it as the single largest correctness risk in the repo.

Keccak is `golang.org/x/crypto/sha3.NewLegacyKeccak256` — stdlib `crypto/sha3` is FIPS-202 only and has no legacy Keccak (ADR-0004).

Tests: copy `nutz-contracts/test/fixtures/claims.json` into `testdata/merkle/` and assert the port reproduces root `0x88b44d7a37b5a4d381e091853e53d8c9e7964de7e1a41037e7e41b0062877591` and every one of its six proofs. Then grow the fixture set here for the cases the contracts fixture does not cover: a single leaf, two leaves, an odd leaf count, duplicate amounts across accounts, and leaves whose hashes sort into a different order than their input order. The last one is the landmine — a wrong `sortLeaves` produces a valid-looking tree with a wrong root, and only a fixture where input order and hash order differ catches it.

## Comments

**2026-09-14 — implemented in `33e9da9`.**

`internal/merkle` ports StandardMerkleTree v1.0.8: direct 224-byte serialiser, `sortLeaves: true`, flat `2n-1` tree with commutative sorted-pair hashing, root at index 0, plus proof generation and a `Verify` that replays a proof the way the Distributor does. Keccak via `x/crypto/sha3.NewLegacyKeccak256`; the Go dependency tree is two modules (`x/crypto` + its `x/sys` requirement).

Root `0x88b4…7591` and all six proofs reproduce from a byte-identical copy of the contracts fixture. The root and claim count are written as **literals** in `tree_test.go` rather than read from the fixture — reading the expected root out of the same file that supplies the claims is not a pin, and a swapped fixture passed until that was fixed.

Five more fixtures added, all generated by OpenZeppelin's own library from the new `tooling/` package (ADR-0005, outside the Go module): single leaf, two leaves, odd leaf count (5), duplicate amounts across accounts, and `unsorted-input.json` whose claims are the exact reverse of leaf-hash order. That last one is guarded by its own test asserting it is *not* already sorted, so a future regeneration cannot quietly neuter the landmine case.

Validation beyond the fixtures: eight mutations of the implementation (no sort, descending sort, single-hashed leaf, order-dependent pair hashing, forward leaf placement, dropped account word, dropped id word, flipped sibling side) each fail the suite; the leaf encoding cross-checks against Foundry `cast abi-encode` (224 bytes, matching digest); and a review agent ran a 300-case randomised differential against the installed OZ v1.0.8 (1–11 leaves, duplicate accounts and amount vectors, `0` and `2**256-1`) with root, every leaf and every proof element matching in all 300. 100% statement coverage, `-race` clean, `go vet` and `staticcheck` clean.
